# VIREON architecture notes

I have kept VIREON as a set of small Python modules rather than splitting it into separate services. That makes it easier for me to run and test on a local machine.

## Main pieces

- Event models check the shape and basic values of incoming synthetic events.
- Signal rules apply configured thresholds to the event data.
- Storage saves events and generated signals in a local SQLite database.
- Evidence and audit records keep references to the input and rule information used in a result.
- The registry stores information about data, model and detector versions used by the prototype.
- The CLI and API provide ways to run a scenario and inspect stored results.
- The dashboard gives a basic browser view of selected information.

## Repeatable evaluation

The signal detector accepts an optional timezone-aware evaluated_at value. If I use the same event, rules, detector version and time, the result can be compared reliably in tests. If no time is passed, the detector uses the current UTC time.

## Current boundaries

The workflow is local and uses synthetic data. The project does not connect to a real pharmaceutical company, hospital, clinical-trial platform or regulator. Its flags are generated by configured software rules and should not be treated as clinical findings or proof of misconduct.

I have not split this into microservices because the current size of the project does not need them. If the code grows, I would first look for a concrete reason to separate a module.
